# Three extensions, one plan each, written for a cloud coding session

Each plan below is a self-contained task for one agent session that has this repository cloned, Python 3, git and bash, and no access to a Proxmox host, a Gitea instance or a model endpoint. Everything a plan asks for is therefore code, tests against fakes, and documentation; the sequence of real `pct` or `qm` commands is asserted by tests, never run. What an operator must still verify on a real host is listed at the end of each plan and goes into the pull request description.

Read first, in this order: `docs/concepts.md` (the terms), `runner/dark/sandbox.py` (the five-method seam every backend implements), `runner/dark/vm.py` and `runner/dark/docker.py` (the two backends), `runner/dark/config.py` (`Host`, `BACKENDS`, `check_backend`), `runner/dark/run.py` (`Runner.launch`, `_Run.reap_all`, `agent_task`), `runner/dark/session.py` (the in-sandbox session executor), `runner/dark/spec.py` (classes and outcomes), `runner/budgets.toml` (`[class.*]`), `runner/tests/fakes.py` and the test file of the module you touch.

Rules for every plan: commit per numbered item with the item named in the message; run `cd runner && bash verify.sh` and `python3 bench/tools/check_tasks.py` before each commit and keep both green; add no dependency; no real hostnames, addresses or ids in code, tests, docs or commit messages, examples only; if an item cannot be done as written, stop and write `BLOCKED: <why>` in the final message instead of guessing. Push the branch and stop; the pull request is opened by the maintainer.

## Plan 1: an LXC backend, so a sandbox can be a clone of a real container

Why: a change to a running service should be rehearsed on a copy of the container that runs it, then applied to the real one. Today a sandbox is a VM cloned from a template or a docker container from an image; nothing clones an LXC container.

1. `runner/dark/lxc.py`: a class `Lxc` implementing the `Sandbox` protocol over ssh to the Proxmox host, with the same `ssh()` helper shape as `vm.Proxmox`. `reachable()` runs `pct list`. `template_ok()` checks that the source container id exists and that the named snapshot exists on it (`pct listsnapshot <id>`), returning `(False, why)` otherwise. `spawn(vmid, name, files, runcmd)`: `pct clone <source> <vmid> --snapname <snap> --full 1 --hostname <name>` (a full clone from the snapshot; do not assume linked clones), `pct set <vmid> --net0 name=eth0,bridge=<bridge>,firewall=1,ip=dhcp`, write `/etc/pve/firewall/<vmid>.fw` with the same default-drop content and `GROUP agentfw` as `vm.Proxmox`, `pct start <vmid>`, then inject without cloud-init: each file with `pct push <vmid> <tmp> <path> --perms <mode>` and the run command as a start script executed with `pct exec <vmid> -- /bin/sh /opt/dark-start.sh` in the background, following how `docker.Docker` builds `/opt/dark-start.sh`. `guest_ip()` parses `pct exec <vmid> -- hostname -I`. `reap()`: `pct stop <vmid>`, `pct destroy <vmid> --purge`, remove the firewall file, and return True only when `pct status <vmid>` fails with "does not exist". Acceptance: `runner/tests/test_lxc.py` with a fake ssh recorder asserts the exact command sequence for `spawn` and `reap`, the firewall file content, the refusal when the source or snapshot is missing, and that `reap` returns False when the status check still answers; `bash verify.sh` green.
2. Configuration: add `"lxc"` to `config.BACKENDS`; `Host` gains `sandbox_container` (the container id to clone), `sandbox_snapshot` (the snapshot to clone from) and `sandbox_bridge`, each with an environment override named like the others and an example line with a comment in `runner/host.toml`; `sandbox.make` builds `Lxc` for `backend = "lxc"`; `preflight` reports `template_ok()` for it like the other backends. The backend also carries `sandbox_pool` (the Proxmox pool a clone is placed in; default `""` = no pool) and `sandbox_allow_in` (the `"<ipv4>:<tcp port>"` clients a clone's firewall lets in, comma separated; default `""` = none besides the service host). Acceptance: `runner/tests/test_config.py` and `test_sandbox.py` cover the new backend name and the three keys; `bash verify.sh` green.
3. Snapshot and rollback on the seam: add `snapshot(vmid, name)` and `rollback(vmid, name)` to the `Sandbox` protocol. `Lxc` implements them with `pct snapshot` and `pct rollback`, `Proxmox` with `qm snapshot` and `qm rollback`, `Docker` raises `NotImplementedError("docker sandboxes have no snapshots")`. The runner does not call them yet; they exist for the applier that will. Acceptance: one test per backend; `bash verify.sh` green.
4. Documentation: `docs/concepts.md` gains "container target" (a sandbox that is a full clone of a real container, taken from a named snapshot, on a bridge that reaches only the service host); `README.md` "What you need" names the third backend in one sentence; `docs/docker.md`'s comparison table gets an LXC column. Acceptance: the three files mention `lxc`; `python3 bench/tools/check_tasks.py` still reports 0 problems.

For the operator to verify on a real host, in the pull request description: that `pct clone --snapname --full` is accepted on the host's storage for a stopped and for a running source; that the firewall file path applies to containers on that Proxmox version; that `pct exec ... &` detaches as expected.

## Plan 2: a long arm, one session for hours over several repositories, judged by a reviewer

Why: the session arm today runs one repository, one branch, with a reduced tool set, for at most the longest class's 1800 seconds, and is judged by hidden tests. Long, judgement-heavy work has no hidden tests; its judge is a second session that reads the branches.

1. Several repositories: `agent_task` (in `run.py`) gains `repos`, a list of `{name, url, base}`, kept beside the single `repo` and `branch` for the existing arms; `session.py` clones each entry into `/work/<name>` on `base` and, at the end, pushes `HEAD` of each to `<delivery branch>` in that repository, one loop where today there is one push; the `DARK: done` tag lists the branches pushed. Acceptance: `runner/tests/test_session.py` covers two repositories with the fake git and asserts two pushes and the tag content; `bash verify.sh` green.
2. A class `long` in `spec.py` and `runner/budgets.toml` with `hard.seconds = 14400`, a `calls` ceiling high enough never to bind (say 2000), `think = "medium"`, no admission (`admit_at = 0`, the operator names the tier); the keep-awake lease and the runner deadline already derive from `env.seconds`, so assert in a test that a long run's deadline and lease are computed from the new value. Acceptance: `test_spec.py`, `test_budget_admission.py` and `test_run.py` cover the class; `bash verify.sh` green.
3. A full tool set on request: a task field `tools = "full"` makes `session.py` launch pi without `--no-extensions --no-skills --no-prompt-templates --no-context-files` and without `PI_OFFLINE=1`; the default stays reduced; the flag is recorded on the ledger `run.end` row. Acceptance: `test_session.py` asserts both argv shapes and the ledger field; `bash verify.sh` green.
4. A reviewer as judge: review mode (`cmd_review` and `session._main_review`) accepts `review_branches`, a list of `{name, url, branch}`, clones each into the review sandbox before the session starts, and the run's outcome is read from the last line of `report.md`, which must be `VERDICT: pass` or `VERDICT: fail` with one line of reason; a missing or malformed line is `fail` with `fail_kind = "no-verdict"`. Acceptance: `test_review_executor.py` and `test_review_run_driver.py` cover clone, pass, fail and missing; `bash verify.sh` green.

For the operator to verify on a real host: a four-hour run against a real Gitea with two repositories, the lease held throughout, and the reviewer's verdict landing in the ledger.

## Plan 3: a user arm, a fresh sandbox that gets only a URL and a task, with a browser

Why: the only verifier today is a hidden test suite. A deployed application should be checked by something that never saw its source: a browser, a task written as numbered steps, a screenshot and a verdict per step.

1. A browser image: `runner/sandbox/Dockerfile.browser` on the existing sandbox image plus Chromium and Playwright for Python (the image's own package manager, pinned), and a `browser_image` key in `Host` with its example line and environment override; `docker.Docker` takes the image to use per spawn (a parameter, defaulting to `sandbox_image`). For the VM backend the plan is the `vm-runtime` tarball precedent in `session.fetch_runtime`, recorded as out of scope in the PR. Acceptance: `test_config.py` and `test_docker.py` cover the key and the per-spawn image; `bash verify.sh` green.
2. A class `user`: `tasks.load_task` accepts `url` (required for this class, refused for others) and `steps`, a list of numbered step texts; `agent_task` carries them; the sandbox for this class gets no repository token and no clone (assert it in a test). Egress: `docker.Docker` joins the sandbox to a second, non-internal network named by a new `target_network` key when the class is `user`; `vm.Proxmox` adds one firewall rule `OUT ACCEPT -dest <target host>` from a `target_host` key. Acceptance: `test_tasks.py`, `test_docker.py`, `test_vm_gitea.py` cover it; `bash verify.sh` green.
3. The executor `runner/dark/user.py`, injected like `session.py`: opens the URL, then for each step asks the model (through the same provider entry the session arm uses) for the next browser action given the step text and the page's accessibility snapshot, performs it with Playwright, takes `/opt/records/steps/<NN>.png`, and appends `{step, verdict, note}` to `/opt/records/steps.jsonl`; the run passes when every step's verdict is `pass`; records are pushed with the same `push_records` path as the session arm. The model is called through a small interface so tests use a scripted fake, and the browser through a driver interface so tests use a fake page. Acceptance: `runner/tests/test_user.py` runs three steps against the fakes, asserts three screenshots named in order, the jsonl content, `pass` and `fail` outcomes, and that no token appears in the records; `bash verify.sh` green.
4. Documentation and the CLI: `python3 -m dark user --task <toml>` runs one user task; `docs/concepts.md` gains "user arm" and "step verdict"; `README.md` lists the command in one line. Acceptance: `test_cli_resume.py` or a new CLI test covers the subcommand; `python3 bench/tools/check_tasks.py` 0 problems.

For the operator to verify on a real host: the browser image builds and starts on the runner host; a sandbox on the target network reaches the application and nothing else; one real task against a test deployment produces the screenshots.
